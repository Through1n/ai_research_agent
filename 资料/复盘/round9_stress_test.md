## 二、话术 3 定向优化结果

### 优化 1：扫描件 OCR 串行 → 并发（最大收益）

`services/library.py`：新增 `OCR_PARALLEL = 3`，批次内 `use_ocr` 时改用 `ThreadPoolExecutor`；
每页传 `doc_cache=None`，让各线程打开**独立的 PyMuPDF 文档实例**（并发访问同一文档非线程安全）；
结果按页号存回 `results` 保证顺序，并按完成顺序实时上报进度。

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 耗时 | 111.87s | **44.91s（2.49x）** |
| chunks | 42 | 43 |
| 覆盖页数 | 13 | 13 |
| OCR 文本 | — | 45572 字符 |
| `28.4` 保真 | 是 | 是 |

### 优化 2：领域综述全程无提示 → 分段进度

- `services/graph.py`：`generate_review` 新增可选 `progress_cb`，拆成
  「① 解析引用图谱结构（社区发现 / 时间线 / 骨干边）」「② 生成综述正文（大模型撰写中，约需 20~40 秒）」
- `ui/page_graph.py`：静态 `st.spinner` 改为 `st.status`，阶段实时反映到标题

实测：触发 2 段进度，综述 2182 字，38.8s。

### 优化 3：大文档进度粒度

`services/library.py`：进度 interval 由固定 50 页改为 `max(10, total // 50)`。
541 页文档由 11 次回调提升到约 54 次，消除长时间无反馈的观感卡顿。

## 三、过程记录：两处「以为是缺陷、实为测试脚本调用错误」

压测第一版出现过两条误报，已核对签名后撤销，记录以防重复排查：

| 现象 | 复核结论 |
|---|---|
| 扫描件检测对 0 字符页返回 `False` | **误报**。`detect_scanned(doc, sample=6)` 接收的是**文档对象**，我却传了单页对象 + 文本。修正后 `v1_img=True / v7=False`，判定正确 |
| `generate_review` 报 `missing 3 required positional arguments` | **误报**。真实签名为 `generate_review(ctx, G, metrics, cornerstone)`，需先 `analyze()` + `classify_papers()` |

> 教训：下结论前先核对函数签名，不能只凭一次调用结果判定产品缺陷。
