### 2.1 LLM 四场景（S1–S4）

**patch 对象**：`openai.resources.chat.completions.Completions.create`

**为什么是这一层**：这是业务代码与 OpenAI SDK 的边界。其下（请求构造、HTTP、SDK 自身重试）被替换，其上（`core/llm.py:_create` 的错误分类 `_classify_error`、退避 `_sleep_backoff`、伪响应 `_fake_response`、`last_error/last_error_kind`、UI 渲染）**全部真实执行**。再往下 patch（如替换整个 `LLMClient`）会跳过分类与重试，取证就不真实了。

**构造的异常全部是 openai SDK 的真实异常类**，且带真实 `httpx2.Response`（openai 3.13 用的是随包分发的 `httpx2`，不是 PyPI 的 `httpx`，这点踩过坑）：

| 场景 | 注入的异常 | 真实对应关系 |
|---|---|---|
| 401 | `openai.AuthenticationError(msg, response=httpx2.Response(401,...), body={...})` | 智谱 Key 无效/过期 → HTTP 401，SDK 抛此类 |
| 429 | `openai.RateLimitError(msg, response=httpx2.Response(429, headers={"retry-after": "2"}))` | 限流 → HTTP 429（带 Retry-After），SDK 抛此类 |
| 超时 | `openai.APITimeoutError(request=...)` | 读取超时时 SDK 抛此类 |
| 断网 | `openai.APIConnectionError(message="Connection error.", request=...)` | DNS 失败/连接被拒/代理拦截，SDK 统一抛此类 |

**超时"真睡 60 秒"的等价性说明**（两条实测支撑，见 §3.4）：

1. **A1 等价性**：patch 传输层 `httpx2.Client.send` 抛 `httpx2.ReadTimeout`（真实读取超时时 httpx2 抛的正是它）→ openai SDK 捕获后包装成 `openai.APITimeoutError` → `core/llm` 分类为 `kind='read_timeout'`，`last_error='Request timed out.'`。**与主场景直接抛 `APITimeoutError` 得到同一个异常类、命中 `_classify_error` 的同一个分支**，故注入等价。
2. **A2 时长缩放**：不真睡 90s，而是把 `LLM_TIMEOUT` 设为 2.0s 并让传输层"挂起 2s 后超时"——每次尝试等待时长与 timeout 成正比。实测 `4×2.0 + 9.0(退避) = 17.0s`，与公式吻合；按线性外推得到默认 `LLM_TIMEOUT=90` 时的 369s。**这是外推值，不是实测值**，报告中已明确标注。

### 3.7 附加实测 D · 框架横幅为什么在主体区看不到

```

  在侧边栏输入框真实填 Key               → LLMClient 每轮重建=False；点击当轮 last_error=有；重绘一轮后=有（横幅会渲染）
```

机制：`ui/sidebar.py:216` 每轮都调 `ctx.set_provider(pid, key)`，而 `services/state.py:132` 的重建条件是 `manual_key != self.llm.api_key`。Key 来自 `.env` / Docker env（侧边栏输入框为空，本仓库默认方式）时该条件恒真 → **每轮重建 LLMClient → `last_error` 每轮被清零**。

叠加第二个问题：`app.py:124-131` 的 `llm_failure_banner(ctx)` 在**页面渲染之前**执行，所以主体区本轮产生的 `last_error` 要等下一轮才可能被渲染——而下一轮它已经被清零了。结果：**主体区 LLM 失败，框架横幅永远不会出现**（S1–S4 探针 B 的实测输出里没有一条横幅文案，可对照）。侧边栏「🔌 测试连通性」因为在 sidebar 阶段就完成调用，横幅能在当轮出现。
