## §0 开始前：30 秒确认部署形态

```bash
docker compose ps
```

**预期**：`ai4s-agent` 一行，`STATUS` 为 `Up ... (healthy)`。

| STATUS 显示 | 判读 | 第一处置动作 |
|---|---|---|
| `Up (health: starting)` 超过 **150 秒** | 超过 `start_period=120s` + 1 轮 `interval=30s`，属异常 | `docker compose logs --tail=80 ai4s-agent` |
| `Up (unhealthy)` | 健康检查连续 3 次失败 | 跳到 §6 症状表 |
| `Restarting` | 进程反复退出 | `docker compose logs --tail=200 ai4s-agent` 看最后一次 traceback |

## §1 首次启动的硬校验：权限与种子（**最优先，别跳过**）

这一节是本轮（Round 13）新加的。原因是全新克隆的宿主机上 **没有 `storage/` 目录**
（被 `.gitignore` 的 `storage/` 与 `.dockerignore:25` 双重排除），容器能不能起来取决于挂载后的属主。

### 1.1 属主必须是 `app`，不是 `root`

```bash
docker compose exec ai4s-agent ls -ld /app/storage /app/storage/uploads /app/storage/chroma /app/logs
```

**预期**：四行的第三个字段（属主）全部是 `app`。

| 实际看到 | 后果 | 第一处置动作 |
|---|---|---|
| 全部 `app` | ✅ 正常，继续 §1.2 | — |
| `/app/storage` 是 `root`，但三个子目录是 `app` | 可用（Dockerfile 第 4 层已把子目录逐个预置并 chown），但**仍建议修** | 见下方 A |
| `/app/storage` 与子目录都是 `root` | ⚠️ **应用起不来**：页面会显示「⚠️ 操作失败：加载依赖模块。**storage/ 目录不可写（容器挂载属主不对）**」（`app.py:43` 的 `isinstance(e, OSError)` 分支），并给出 `chown -R 10001:10001 ./storage ./logs` 的处置建议（`app.py:45`）| 见下方 A |

**A. 处置动作（二选一，别两个都做）**：

```bash
# A-1 推荐：删掉卷让它按镜像内容重新 copy-up（会丢失已有文献库数据）
docker compose down
docker volume rm <项目名>_app_storage        # 名字用 docker volume ls 查
docker compose up -d
docker compose exec ai4s-agent ls -ld /app/storage        # 复验

# A-2 保守：就地改属主（保留数据）
docker compose exec -u root ai4s-agent chown -R 10001:10001 /app/storage /app/logs
docker compose restart ai4s-agent
```

> 不走 Docker、直接在 Linux 裸机上跑的场景，见 `资料/CROSS_PLATFORM.md §8.4`
> （同一条规则，只是没有卷这一层）。

> ⚠️ 为什么必须查这一项：`storage/` 对 uid 10001 不可写时，`config.py:42` 的
> `_d.mkdir(parents=True, exist_ok=True)` 会抛 `PermissionError`。
> CPython `Path.mkdir` 源码的 `except OSError: if not exist_ok or not self.is_dir(): raise`
> ——子目录不存在时 `is_dir()` 为 False，**权限错误不会被 `exist_ok=True` 吞掉**，
> 且其注释明写 "could give priority to other errors like EACCES or EROFS"。
> 该异常发生在 import 期，被 `app.py:34` 的依赖导入兜底捕获。
> ⚠️ 文案已在我交付前被队友改过：现在 `app.py:43` 用 `isinstance(e, OSError)` 分流，
> 权限类会显示「storage/ 目录不可写（容器挂载属主不对）」而不是「依赖未安装」。
> 所以**看到这句就是权限问题，别再去查 requirements.txt**。
> （本机为 Windows，`chmod` 无法复现 Linux 的 EACCES，此项**按源码与 Linux 语义推导，未在本机实测**。）

### 1.2 种子文件必须存在且类型正确

```bash
docker compose exec ai4s-agent sh -c 'for f in library.json memory.json user_profile.json; do printf "%s: " "$f"; cat "/app/storage/$f"; printf "\n"; done'
```

**预期**（逐字节比对，一个字符都不能差）：

```
library.json: {"papers": {}, "paper_order": [], "chunks": [], "likes": {}}
memory.json: {"notes": [], "kv": {}}
user_profile.json: {}
```

**这一项现在是「体检」不是「救命」**：本轮早些时候，类型写错确实会让应用起不来；
但在交付前，队友已给 `services/state.py` 加了 `_ensure_lib_dict`（`:181-190`）、给
`core/memory.py` 加了 `_normalize()`（`:16-30`），**三种错误写法现在都能优雅兜住**
（我已用真实解释器复测通过，见 `资料/复盘/round13_deploy_finish.md §2.5`）。

所以真正的判据是：**种子必须存在**（存在 = 命名卷 copy-up 真的发生了，属主也大概率对了）。
内容对不对，已经不再是生死问题。

| 实际看到 | 判读 |
|---|---|
| 与上面三行一致 | ✅ 正常 |
| 三个文件都在，但内容被改过 | ✅ 仍可用（代码有兜底）。但**要查 §1.1 的属主**：内容被改说明卷不是本次新建的 |
| `library.json` 是 `[]` | ⚠️ 可用但不对：`services/state.py:90` 的 `_ensure_lib_dict` 会回落成默认字典。**请按上面三行改回来**，否则会被误读成"文献库被清空了" |
| `memory.json` 是 `{}` | ⚠️ 可用但不对：`core/memory.py:14` 的 `_normalize` 会补 `notes`/`kv`。同上，改回来 |
| `user_profile.json` 是 `[]` | ⚠️ 可用但不对：`_normalize` 会回落成 `{}`。同上，改回来 |
| **文件不存在** | ❌ 不会崩（读取都有 try/except），但说明**命名卷没做 copy-up** → 直接回 §1.1 查属主，这才是真问题 |

### 1.3 确认没有把密钥烤进镜像

```bash
docker compose exec ai4s-agent sh -c 'env | grep -iE "KEY|TOKEN" | sed "s/=.*/=<已隐藏>/"'
```

**预期**：只看到变量名（`ZHIPU_API_KEY=<已隐藏>` 之类），这是运行期注入，正常。

再确认镜像层里没有真值：

```bash
docker history <镜像名> --no-trunc 2>/dev/null | grep -iE "ZHIPU|DEEPSEEK|DASHSCOPE|sk-" | head
```

**预期**：**无任何输出**。有输出 = 密钥被打进镜像层，立即作废该 Key 并重建镜像。

### 1.4 自动化门禁：四条命令一次性证明核心链路（建议跑）

比手动点三十次更快、也不会漏。四条**必须串行**（见下方警告）：

```bash
# ① 语法/字节码
docker compose exec ai4s-agent python -m compileall -q core services tools ui app.py config.py
# 期望：exit 0，无输出

# ② 单元测试
docker compose exec ai4s-agent python -m unittest discover -s tests
# 期望：Ran 230 tests ... OK

# ③ UI 冒烟：九个页面逐个渲染，捕获异常
docker compose exec ai4s-agent python scripts/_smoke_ui.py
# 期望：exit 0；输出含「9 个菜单项全部有路由」「9 项导航均真正切换到位」，0 异常

# ④ 阅读链路冒烟
docker compose exec ai4s-agent python scripts/_smoke_read.py
# 期望：PASS 62 / FAIL 0
```

**为什么在容器里跑得起来**（都已核实，不是推测）：

- `.dockerignore` **不**排除 `scripts/`、`论文样本/`、`演示语料/`、`lib/`、`static/`，
  两个冒烟脚本依赖的 `论文样本/1810.04805v2.pdf` 等素材都在镜像里。
  （`tests/` 原本是被排除的，为了让门禁 ② 能在容器内跑，本轮已改为不排除 —— 代价 44KB。）
- `scripts/_smoke_ui.py` 用的是 `streamlit.testing.v1.AppTest`（`:22`），
  **进程内渲染，不需要浏览器 / playwright**，容器里没有任何额外依赖。
- `scripts/_smoke_read.py` 显式模拟「未填 API Key」（`:384` `available = False`），
  **不需要真 Key**，也不访问网络。
- 它还会自己写 `storage/llm_failures.log` 并断言其存在（`:348-349`）——
  所以门禁 ④ **顺带验证了 `/app/storage` 对 uid 10001 可写**，与 §1.1 是同一件事的两种查法。
  **这一条 FAIL 时，先回 §1.1 查属主**，别去查脚本。

> ⚠️ **`_smoke_ui.py` 与 `_smoke_read.py` 必须串行**，不要并行跑：
> 后者有依赖 sleep 退避时长的断言，并行会偶发假 FAIL（crossplat 实测结论，我未复现）。
>
> ✅ **上面四个期望值是队友修完 .py 之后重跑确认过的**（crossplat 串行实测，2026-10-14）：
> `G1 compileall → 0`、`G2 unittest → 18 OK`、`G3 → 9 页 0 异常`、`G4 → PASS 60 / FAIL 0`。
> （以上为 2026-10-14 当日实测原值，保留不改；2026-10-25 复跑已升至 230 / 62，上表「期望」列已是新口径。）
> ⚠️ 但那是**本机（Windows）实测，容器内仍未实测**（本机无 docker）。
> 第一次在容器里跑，请先看**有没有 FAIL 项**，不要只比对总数。

### 4.6 已知安全边界：XSRF 防护当前是关着的（有意保留，不是漏配）

`.streamlit/config.toml:23` `enableXsrfProtection = false`。

- **为什么现在是关的**：改成 `true` 之后能否在 Nginx 反向代理下照常工作，
  **本轮没有真实部署环境可验证**。XSRF 校验一旦在代理后面误触发，表现是评委点任何按钮
  都失败、页面直接打不开 —— **打不开站点，比少一道 XSRF 保护严重得多**。
  先交付一个能访问的站点，再谈加固。
- **什么时候必须开回 `true`**：从「一次性演示」转为**公网长期部署**时。
- **怎么改**：编辑 `.streamlit/config.toml`，把 `enableXsrfProtection` 改成 `true`，
  然后 `docker compose restart ai4s-agent`
  （`config.toml` 是挂载进容器的，**不需要重新 build**）。
- **改完只验一件事**：用**无痕窗口**打开外网地址，点一个会改状态的按钮
  （推荐 `一键加载演示数据`）→ 必须仍然弹出 `✅` 成功提示。
  若变成报错或无响应，说明代理链路下 XSRF 校验误伤 —— 先改回 `false`，
  再查 Nginx 是否正确转发 `Origin` / `X-XSRF-TOKEN` 头。

> 这一条**不设 checkbox**：演示阶段的正确动作就是保持 `false`；
> 只有转为公网长期部署时，才执行上面的「改 + 验」。

- [ ] 点一次 `🎭 演示模式示意图谱` → 图谱渲染出节点
- [ ] **不填 Key** 点一次 `抽取标题/作者/机构/摘要 + 判断排版` → 确认弹的是人话提示而不是静默
- [ ] 填 Key 后点一次 `🔌 测试连通性` → `✅ 连通性正常`
- [ ] F12 看源码搜 `sk-` / `ZHIPU` → **必须零命中**
- [ ] §1.3 的 `docker history` 复查 → 无输出
- [ ] 确认 `.env` 没有被 push 到 GitHub
- [ ] 确认交付物里没有 `.workbuddy/`：先 `unzip -l <包名>.zip > /tmp/_pkg.txt; echo "unzip=$?"`，再 `grep -q -i workbuddy /tmp/_pkg.txt; echo "grep=$?"` → 必须 **`unzip=0` 且 `grep=1`**（`grep` 0=有残留，1=干净，≥2=命令本身出错）

> **为什么是这条（不是"提醒别拷贝"）**：`.workbuddy/memory/` 下有 11 个内部工作记录文件（实测约 132 KB），已从版本控制移除（`git ls-files .workbuddy` = 0）但**仍在磁盘上**。四条交付路径的实际状态：
>
> | 路径 | 安全？ | 机制 |
> |---|---|---|
> | Docker 镜像（`COPY . .`） | ✅ | `.dockerignore:101` 已排除 `.workbuddy/` |
> | `git clone` / `git archive` | ✅ | `.gitignore:11` 已排除，且 HEAD 内 `.workbuddy` 文件数为 0 |
> | `scripts/release.py` 打的 zip | ✅ | **白名单**：只遍历 `INCLUDE_TOP_ITEMS`（`scripts/release.py:36-48`），不在白名单里的一切天然不进包；即使 `EXCLUDE_NAMES`（`:51-55`）漏写 `.workbuddy` 也进不去 |
> | 手工整目录拷贝 / `zip -r x.zip .` | ❌ **敞口** | 两个 ignore 文件都不生效 |
>
> 关键点：第三条的安全性来自**白名单**而不是"有人记得排除"——黑名单漏一项就漏一项，白名单是"没列进去就进不来"。但也正因如此，谁把 `INCLUDE_TOP_ITEMS` 加上一行 `"."`，脚本**照样 exit 0、照样出一个看起来正常的包、没有任何警告**。所以 `unzip -l | grep -i workbuddy` 是唯一的独立抓手：它验的是**交付物本身**，不依赖任何脚本或人的记性。**这条是"识别并自证"，不是"风险已消除"**——手工拷贝那条路径仍然敞口。
>
> **为什么不写成 `unzip -l x.zip | grep -i workbuddy` 一行**：管道只暴露 `grep` 的退出码。包不存在或损坏时 `unzip` 把错误写到 stderr、stdout 为空，`grep` 照样返回 1 —— 于是"必须无输出"**假通过**，你手上根本没有包也会判干净。先落盘再查，才能把 `unzip` 自己的失败暴露出来。
