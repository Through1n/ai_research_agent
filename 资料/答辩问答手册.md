## 一、10 个「评委一定会问」的难题

### 【① 代码实现细节】

#### 题 1：「你的 RAG 检索用的什么 embedding？为什么选它？」

**直接回答**：chroma 自带的 ONNXMiniLM_L6_V2，384 维，本地 ONNX 推理，不出网。

**技术佐证**：关键不在于选它，在于怎么用。`_build_embed_fn@services/state.py:43` 持有单例并预热（`:59`）——默认实现每次 embed 都新建实例，实测每次 128ms 重建会话、1 条文本 155ms 里 128ms 是建会话，一次检索调 5 次白付 640ms；`_EMBED_CACHE@services/rag.py:65` 再缓存 chunk 向量，上限 8000 条约 12MB。

**承认局限**：它是英文模型，中文提问配英文文献余弦天然偏低，实测 v1/v7 整篇只有 0.891292，够不上 0.90 阈值。

**未来规划**：换 bge-small-zh，把去重阈值整套重标，同题做 A/B 对照再切。

---

#### 题 2：「混合检索怎么融合的？RRF 的 c 为什么是 60？」

**直接回答**：Dense+BM25 双路 RRF，c=60。但纯 RRF 不够，我改了三轮。

**技术佐证**：`rrf_fuse@services/rag.py:258` 是标准式；问题是库里 541 页教材占 88% chunk，RRF 前几名被单一来源吃满，正确答案进不了 top-k。所以 `POOL_FACTOR@services/rag.py:53` 把池放大到 final_k×4，`cap_by_source@services/rag.py:267` 按来源轮转截断（每来源 cap = max(2, ceil(final_k/来源数))），`VERSION_DEDUP_MIN@services/rag.py:55`=3 才丢旧版。

**承认局限**：c=60 是论文经验值，我没在自己语料上网格搜过，说不出"为什么不是 50"。

**未来规划**：网格搜 c 和 POOL_FACTOR，用人工标注集评 nDCG@6。

### 【② 技术选型】

#### 题 3：「为什么不用 LangChain 或者 LlamaIndex？」

**直接回答**：三个字——可控。参数在哪、为什么这个值，我得能当场翻给评委看。

**技术佐证**：`requirements.txt` 一共 13 个依赖，没有 langchain。22 个 Function Schema 自己注册（`build_registry@tools/definitions.py:371`），专家白名单 `EXPERTS@core/router.py:22`。阈值全是自持常量，集中在 `services/rag.py:46-55`、`config.py:134-138`。套框架后这些埋在默认对象里，调不动也说不清。

**承认局限**：代价是工具生态得自己搭，PubMed、Web 检索都是自己写的，功能比框架少。

**未来规划**：把 RAG 链路抽成接口层，可选适配 LlamaIndex 的检索器做能力对照。

---

#### 题 4：「PDF 版面解析为什么自己写，不用 GROBID / MinerU？」

**直接回答**：GROBID 要起 Java 服务，MinerU 要 GPU，演示机器上都要不起。

**技术佐证**：`_detect_two_columns@services/parsing.py:171` 要四条必要条件同时成立才判双栏，最硬的是横跨否决——单栏论文的长正文行必然横跨中线，这是区分单双栏最可靠的证据。实测 1111 页单栏语料误判率 **19.1%→0%**，同时真双栏 BERT 正文页 **10/10** 仍被正确识别，不是靠"永远判单栏"刷指标。

**承认局限**：三栏和跨栏表格判不了，判错就保守退回单栏；公式只保留文本。

**未来规划**：版面判定做成可插拔模块，复杂版式接 layoutlmv3 之类的模型。

### 【③ 数据验证】

#### 题 5：「你的抗幻觉准确率怎么量化？有指标吗？」

**直接回答**：没有端到端的"幻觉率"单值，我用四层可复跑的判据代替，不编一个数糊弄。

**技术佐证**：拒答闸门 top 相关度低于 0.35 一次 LLM 都不调（`services/rag.py:834`）；引用覆盖率阈值 `SUSPICION_THRESHOLD@core/guardrails.py:30`=0.15，且 `_overlap@core/guardrails.py:64` 刻意不用 Jaccard——来源 chunk 1200 字会把 Jaccard 稀释到接近 0，正常引用也被误杀；数字核验 `find_unverified_numbers@core/guardrails.py:287`。

**承认局限**：没有人工标注的 gold set，我只能说"抓到多少"，说不出"漏了多少"。

**未来规划**：标注 200 条问答做 gold set，算拒答的精确率和召回率。

### 【④ 失败案例】

#### 题 7：「你的系统在哪类 PDF 上会失败？」

**直接回答**：三类会翻车：扫描件没 OCR、加密或损坏、三栏和跨栏表格。

**技术佐证**：`detect_scanned@services/parsing.py:55` 抽样 6 页判扫描；没配视觉模型时 `_validate_prepared@services/library.py:484` 在 `:510` 写 `scanned_no_ocr` **直接拒收**——不是"效果差一点"，是不入库。541 页官方教材实测 **537 页提取、4 页无文本层、failed_pages=0**。

**承认局限**：表格只文本化进 chunk，没做单元格级结构化检索。

**未来规划**：接本地 OCR 引擎兜底，表格转结构化单独建索引。

#### 题 8：「现场断网或者 Key 失效了怎么办？最坏转多久？」

**直接回答**：不会白屏。最坏约 45 秒转圈，然后给人话降级，不是静默失败。

**技术佐证**：`_classify_error@core/llm.py:220` 分七类，401/403/400 不可重试、立即失败；`config.py:123 LLM_TIMEOUT=45`、`config.py:128 LLM_RETRY_BUDGET_SEC=20`（原先 90s×4 次≈369s，台上转 6 分钟）；429 尊重 Retry-After 但封顶 5s（`core/llm.py:47`）。降级响应带 `DEGRADED_FLAG@core/llm.py:60`，UI 侧 `llm_failure_banner@ui/common.py:390` 给"人话+可能原因+怎么办+日志位置"。

**承认局限**：预算是硬编码秒数，慢网络下可能过早放弃本可以成功的请求。

**未来规划**：预算按错误类型分档，并在侧边栏做成现场可调。

## 二、5 个刁难问题

### 刁 1：「你这个是套壳吧？底层都是智谱的」

先认一半——模型确实不是我的，用的是智谱 glm-4-flash。

但"套壳"这词我得掰一下。如果是"调个 API 包个界面"，那我这 22 个工具、四道抗幻觉防线、版面感知解析就全是白写的。您可以随便挑一层让我现场翻：检索层 `drop_stale_versions@services/rag.py:91`，护栏层 `check_citation_support@core/guardrails.py:96`，解析层 `_detect_two_columns@services/parsing.py:171`，沙箱层 `validate_code@core/sandbox.py:27`。模型是发动机，但发动机不决定这车能不能在沙地上跑。

真要说"套"，我套的是 OpenAI 兼容协议那一层——但那是故意的。内置 5 个 Provider（`PROVIDERS@core/providers.py:33`）：智谱、DeepSeek、通义、OpenAI、本地 Ollama，侧边栏切一下，业务代码一行不动。所以准确说法是：**我套的是协议，不是某一家**。明天智谱倒闭，我今天下班前就换完。
