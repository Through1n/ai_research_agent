## 3. 已应用的高风险修复（代码层，Round 13）

### 修复 A（P1，高）—— 超时窗口
- `config.py:123` `LLM_TIMEOUT`：`90.0` → `45.0`
- `config.py:128` `LLM_RETRY_BUDGET_SEC`：`45.0` → `20.0`
- 效果：首次尝试 45s 后预算即截断，**失败最坏等待从 ≈90s 压到 ≈45s**。
- 代价（知情）：单次成功请求时间窗从 90s 缩到 45s；`glm-4-flash` 常规 2–8s 足够，长综述 / Agent 多步任务若真需 >45s 会降级占位。
- 现场想更严：env 设 `LLM_TIMEOUT=25`（最坏 ≈25s）。

### 修复 B（P2，中高）—— 429 退避封顶
- `core/llm.py:47` `RATE_LIMIT_RETRY_AFTER_CAP`：`10.0` → `5.0`
- 效果：服务端 `Retry-After=60` 时，最坏从 `3×10=30s` 降到 `3×5=15s`。
- `MAX_RETRIES=3` 不变。

### 修复 C（P3，中）—— 降级占位不进数字核验
- `services/rag.py:883` 与 `:890`：`unverified = [] if _degraded else (find_unverified_numbers(...) + find_unverified_codes(...))`
- 效果：降级态（`_degraded=True`）下不再把占位文案里的 `401 / 403 / 1001 / 429 / 1113` 当成「模型编的数字」报出。
- 影响面：只影响降级态；正常成功路径 `unverified` 完全不变。

## 4. 现场提醒（已同步彩排脚本）

1. **超时 / 断网那一档，别在台上干等**——默认最坏 ≈45s。要么信任修复 A，要么直接切
   「一键加载演示数据」讲离线链路（本地解析 / 检索 / 图谱不受影响）。
2. **演示「Key 失效」时，清空侧边栏输入框没用**（`.env` 兜底仍在，`available` 仍为 True）。
   要真失效：改 `.env` 或临时换成错 Key，再点「🔌 测试连通性」。
3. 真遇 429/401：修复 C 已消除「以下内容未在来源文本中找到对应依据：401、403、1001」的噪声；
   若仍出现，属已知显示瑕疵，**直接说明即可，别被评委问住**。
4. S7c/S7d（轻微损坏 PDF）：MuPDF 自愈打开后会静默当成「查重命中 100%」而非「文件可能损坏」，
   不崩溃但易困惑——现场尽量用完好 PDF 演示上传。
