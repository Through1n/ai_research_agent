## 一、组织方式：为什么这么分工

用户要求「分出 10 个 agent 相互比对数据，一部分当评委、一部分当考生，不断复盘」。
落地为**三轮双轨制**，核心是两个约束：

| 约束 | 做法 | 起到的作用 |
|---|---|---|
| **文件所有权隔离** | 每个"考生" agent 有独占文件清单，prompt 明文禁止越界；共享热点（core/llm.py、config.py）指定唯一 owner 或"只 import 不改" | 6 个 agent 并行改同一代码库零覆盖冲突 |
| **评审范围重叠** | 4 个"评委"的审计范围有意交叉，同一模块被两人独立审计 | 交叉验证防虚报——"损坏 PDF 静默入库"被评委 A、D 同时独立命中，坐实为真缺陷 |

评委铁律：**只读取证，唯一允许写的文件就是自己的评审报告**。禁止 Edit/Write 任何源码、
禁止 git 操作、禁止 pip install。报告要求「虚报会被交叉审计抓出来」。

## 六、三条最值钱的教训

1. **必须在 prompt 里写死 Python 解释器路径**。
   本项目真实环境是 `anaconda3/envs/ai_research`，前 6 个考生全部用错成 base 环境，
   于是集体误判"环境缺依赖、测试跑不了"——实际 `unittest` 是 18/18 通过的。
   一个错误的路径，让整轮自验数据全部失真。

2. **「不可信 agent 自述」这条铁律是对的，但要靠机制落地**。
   最致命的 NameError 之所以被考生的自测漏掉，是因为它的故障注入只覆盖**失败路径**，
   永远走不到那一行。是评委用 AppTest 真实点击才复现的。
   → 教训：故障注入不等于功能测试，**必须模拟真实用户操作路径**。

3. **一批并行 agent 控制在 4 个以内**。
   首轮一次派 6 个触发 429 频率限制（第 6 个创建失败，虽后续证实其代码其实已写完）。
   降到 2-4 个/批之后全程无中断。
