# 话术 7：问答响应速度优化报告（流式 + 检索提速）

> 测量环境：Windows / Python 3.11（conda 环境 `ai_research`）/ 真实智谱 API
> 文献库：1480 chunks / 5 篇（含 541 页大书）
> 所有"改前"数字均通过 `git stash` 切回改动前代码、用**同一脚本在同一时段**测得，
> 避免不同批次机器负载造成的误判。

---

## 一、目标与结论

| 目标 | 要求 | 实测结果 | 判定 |
|---|---|---|---|
| 用户看到第一个字 | < 2s | **1.62s**（3 题 × 3 轮平均） | ✅ 达标 |
| 单轮问答总耗时 | < 8s | **7.12s**（3 题平均；Q1 3.80s / Q2 3.21s / Q3 14.35s） | ⚠️ 平均达标，Q3 超 |

改前该指标 = **11.56s / 16.23s**（非流式，用户必须等全部生成完才能看到任何内容）。

**一句话结论**：用户从"等 11.6 秒才看到答案"变成"1.6 秒见首字、逐字流出"，
主观提速 5.8～11.3 倍；检索阶段本地耗时压缩 35.8 倍（6.08s → 0.17s）。

## 二、耗时拆解（改前）

用 `time.perf_counter()` 打点 + `cProfile` 剖析 `retrieve()`，稳态 3 次取平均：

| 阶段 | 改前耗时 | 占比 | 说明 |
|---|---|---|---|
| `retrieve()` 合计 | **6.08s** | — | 本地计算，不含 LLM |
| └ ONNX `initialize_session` | 1.539s（12 次） | 25% | **每次 embed 都重建推理会话** |
| └ `score_sources` | 1.576s（3 次） | 26% | 每次重算 chunk 正文向量 |
| └ `dense_search` | 0.69s（4 次） | 11% | 每次 chroma 内部再 embed 一遍 |
| └ 其他 | 约 2.3s | 38% | 模型加载、BM25、融合 |
| LLM 生成（裸调用） | 8.30s | — | 外部 API，本地不可控 |
| 端到端 `answer()` | **11.56s**（Q1） | — | |

**两个反直觉的发现**：

1. **瓶颈根本不是 LLM，而是本地 embedding 调用**。
   chroma 的 `DefaultEmbeddingFunction.__call__` 源码是
   `return ONNXMiniLM_L6_V2()(input)` —— **每次调用都新建一个实例**，
   而 ONNX 推理会话是该类上的 `cached_property`，实例一换缓存即失效，
   于是每次 embed 都重新 `initialize_session`（约 128ms）。
   实测：embed 1 条文本 155ms，其中 128ms 是建会话，真正推理不到 30ms。
   一次检索调 5 次 embed = 白付 640ms。

2. **`score_sources` 被调用 3 次，每次都重算同一批 chunk 的向量**。
   chunk 入库后正文与 id 均不可变，这些向量完全可以缓存。

## 三、优化项（共 5 项）

| # | 优化 | 位置 | 机制 | 单项收益 |
|---|---|---|---|---|
| 1 | **ONNX 会话持久化** | `services/state.py:42` `_build_embed_fn()` | Container 持有 `ONNXMiniLM_L6_V2()` 单例并在构造时预热，替换每次新建实例的 `DefaultEmbeddingFunction` | 单次 embed 155ms → 28ms；整轮检索省约 640ms（**最大单点**） |
| 2 | **chunk 正文向量缓存** | `services/rag.py:63-73`、`408-428` | 按 `(chunk_id, 文本长度)` 缓存向量，容量上限 8000（约 12MB）；删文时 `clear_embed_cache()` 失效（`services/library.py:1073` 起） | 消除同轮内重复编码、跨轮复用 |
| 3 | **第三次打分复用 `pool_scores`** | `services/rag.py:581` | `sources ⊆ fused_pool`，用同一组 `(query, variants)` 已算好的分；仅 `cap_by_source` 从意图排名额外引入的 chunk 走 `missing` 补算 | 省掉一整轮 embed（约 440ms） |
| 4 | **变体批量 embed + `query_embeddings`** | `services/rag.py:226` `dense_search_vec()`、`545` | 变体向量一次算好，再逐个 `query_embeddings` 检索（实测 `query_texts` 164ms vs `query_embeddings` 25ms，返回 id 序列一致） | 4×164ms → 208ms + 3×25ms |
| 5 | **Phase 1 改走向量路** | `services/rag.py:485` | 绕开 chroma 内部那个"每次重建会话"的默认 embedding 函数 | 164ms → 50ms |

### 关键正确性保障

- `dense_search_vec` **失败返回 `None` 而非空列表**（`services/rag.py:226`）。
  空列表是"库里没候选"的合法结果，调用方必须能区分二者并回退 `dense_search`；
  否则向量路会静默失效、只剩 BM25 在撑——这种降级没有日志、极难察觉。
  （此缺陷是被单元测试 `test_bm25_works_for_chinese_query` 抓出来的。）
- 改动前后**检索结果逐位一致**：4 个查询的 chunk id 序列与 score 全部相同（见第五节）。

## 六、附带修复：答案自相矛盾（抗幻觉）

压测中发现一个**比慢更严重**的问题：

> 改前 Q1 答案：
> "Transformer 使用的 Adam 优化器的 beta1 是 0.9，beta2 是 0.98【1】【2】。
> **资料中没有提供 beta2 的具体值，因此无法确定 beta2 的值【3】。**"

三个来源（v1 / v7 / v1_img）**都明确写着 β2 = 0.98**，后半句纯属模型编造，
而 `unverified=[]` —— 数字校验通过（0.98 确实在来源里），否定陈述无从查证。

**根因**：`ACADEMIC_SYSTEM` 第 3 条要求"资料不足时必须说明无法确定"，
模型据此在已给出确定答案后仍追加一句相反表述。

**修复**：`core/guardrails.py:478` 新增第 7 条约束——

> 7) **禁止自相矛盾**：一旦已依据资料给出确定答案，不得再补充
> "资料未提供/无法确定/未提及"等相反表述——自相矛盾比答错更严重；
> 同一结论在多个来源中一致时只陈述一次，不逐来源重复、不追加否定补充句。

**效果**（连跑 2 次均一致）：

> 改后 Q1 答案：**"Transformer 的 beta1 和 beta2 分别是 0.9 和 0.98【1】【2】【3】。"**

矛盾否定词检测：无。耗时 5.5s / 2.6s。

## 七、未达标项与诚实说明

1. **Q3 总耗时 14.35s > 8s**：输出是长约 800 字的 Markdown 对比表，
   受模型生成速度限制（约 30–50 tokens/s），本地无法压缩。
   但用户 **1.44s 即见首字**，符合"前 2s 内看到第一个字"这一更重要的体感指标。
   若必须压总数，只能限制对比表行数——那属于删功能，不采纳。

2. **端到端绝对值有波动**：受智谱 API 负载影响，不同批次 ±30%。
   因此本报告以"同脚本同时刻 git stash 对比"的检索耗时（6.08s → 0.17s）
   作为最可靠证据，端到端数字仅作体感参考。

3. **首轮冷启动** 3.62s：已通过 Container 构造期预热把模型加载挪到启动阶段，
   会话内第 2 轮起 1.07～1.29s。
