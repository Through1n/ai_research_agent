## 6. 缺陷清单与修复

### F1（P0，已修复并线上验证）WebSocket Origin 白名单 403

**现象**：全白 + 10 条 `WebSocket connection to 'wss://…/_stcore/stream' failed:
Error during WebSocket handshake`。

**根因**：反向代理后的浏览器连 Streamlit WebSocket 一定带 `Origin`，而
`server.corsAllowedOrigins` 默认只含 `streamlit.io` / `*.streamlit.app` /
`share.streamlit.io` / `localhost`。本域名不在其中 → 403 → 全白。
`curl -s "$URL/_stcore/host-config"` 可直接看到那个不含本域名的 `allowedOrigins` 数组。

**修复**：启动参数 `--server.enableCORS=false`，使
`streamlit/web/server/starlette/starlette_websocket.py:189` 的
`is_url_from_allowed_origins()` 直接返回 True。

**验证**：`scripts/_ws_handshake.py` 三例全 `101`；JS 报错 10 → 0。

**注意**：`host-config` 的 `allowedOrigins` 数组**修复后仍显示默认白名单**——它取自
`client.allowedOrigins` 选项、与 `enableCORS` 无关，**不能**当修复未生效的证据。
（这一点比初判时更谨慎，特此记录。）

### F2（P0，本轮主凶，已修复并线上验证）embedding 模型同步下载堵死首帧

**现象**：WS 修好后**仍然全白**，但这次**零报错**。等 183s 导航框不出现、9 页点不到、
body 仅 4 字。

**根因链**（逐环取证）：

```
app.py:86                    ctx = get_container()               ← 模块级，首帧路径上
  services/state.py:70         Container.__init__
    services/state.py           _build_embed_fn()
      chromadb onnx_mini_lm_l6_v2.py:269   __call__
        _download_model_if_not_exists()
          → https://chroma-onnx-models.s3.amazonaws.com/all-MiniLM-L6-v2/onnx.tar.gz
            83,178,821 B，sha256 钉版
```

Streamlit 的渲染模型是**「整段脚本跑完才发首帧」**。脚本卡在 `_build_embed_fn()` 那一行，
一帧都发不出来 → 全白 + 零交互 + 零报错。**唯一线索是右上角的 `Stop` 按钮**
（它表示「脚本仍在运行」）。

**为什么下载完不成**：实测该 S3 域名在境内网络「连接建立但 body 传输挂死」：

```
$ curl -sI https://chroma-onnx-models.s3.amazonaws.com/.../onnx.tar.gz
HTTP/1.1 200 OK                    ← 握手正常
$ curl -s --max-time 5 -o /dev/null -w "%{size_download}"
0 B                               ← 5 秒 0 字节
```

chroma 的 `tenacity` 重试 3 次且**每次无超时上限**，下载永不完成。
模型解包后 6 个文件共 91,332,068 B。

**讽刺点**：`fn(["warmup"])` 是话术 7 为**本地提速**故意加在启动期的。本地热缓存下它是
优化，**线上冷缓存下它堵死首帧——同一个优化在不同缓存状态下语义相反**。

**修复（两层，缺一不可）**：

| 层 | 改动 | 作用 |
|---|---|---|
| 代码层 | `services/state.py` 新增 `_EMBED_*`：`warm_embed_async()` 后台预热 + `get_embed_fn()` 有界等待（默认 90s，`AI4S_EMBED_WAIT_SEC` 可调）+ 人话降级 | 首帧与模型下载彻底解耦，**任何**冷缓存状态下页面都能出来 |
| 部署层 | 88 MB `onnx/` 随发布包上传；`start_app.sh` 启动 streamlit 前拷进 `$HOME/.cache/chroma/onnx_models/all-MiniLM-L6-v2/onnx/` | chroma 的跳过判据是那 6 个文件齐全 → **连下载都不发生** |

**验证（判决性）**：`scripts/_test_coldstart_firstframe.py` 三个桩：

| 桩 | 模拟 | 首帧到达 | 9 个导航目的地 |
|---|---|---|---|
| A | `_build_embed_fn` 抛异常（下载失败） | 5.5s | ✅ 全就位 |
| B | `_build_embed_fn` 永久睡眠（**S3 挂死，线上真实形态**） | **1.4s** | ✅ 全就位 |
| C | 模型正常就绪（对照） | — | ✅ `embed()` 语义不变，0.0ms 直通 |

修复前桩 B 会永远等下去（线上实测 183s+ 无果）；修复后 1.4s 出首帧。

**附带加固（commit `bff3416`）**：模型确实拿不到时不能把功能链路打死。
`_paper_embedding` / `_paper_fingerprints` 失败返回降级值**并**把人话原因写进
`ctx.embed_degraded_reason`，文献库页用 `st.caption` 明示「语义检索模型未就绪…论文已正常
入库，但跨版本内容匹配/智能去重暂不可用」（不用 `st.error`，非致命不刷红）；
`ui/page_graph.py` 降级为关键词重合度建边且口径差异随图谱包持久化；
`ui/page_search.py` 相关性得分按 0.0 并说明排序改由开源代码/点赞/研究画像决定。
**每处降级都对用户可见，没有静默降级。**

### F3（P1，观察项）`start_app.sh` 不在 git，与仓库内 Dockerfile 参数分叉

部署用的 `start_app.sh` 是仓库外文件，`git ls-files` 0 命中；仓库内 `Dockerfile` 自
round12 `8cb6b03` 就带 `enableCORS=false`。**仓库是好的，部署用的是另一套仓库外启动器**。

一度据 mtime 推断「线上跑的是旧启动器」——**该推断已被浏览器级证据证伪**（WS 403→101、
JS 报错 10→0，只有新启动器能带来）。但 mtime 风险本身是真的。
**建议**：把 `start_app.sh` 收编进仓库 `scripts/`，部署包里软链过去。（待办，未实施）

### F4（P2，观察项）88 MB 模型使部署包从 8.2 MB 涨到 96 MB

预置模型是 F2 部署层修复的必要代价。压缩无效（`gzip -6` 后 82.8 MB，仅省 8%）。
若平台对上传体积敏感，备选是 git LFS 或对象存储。当前可接受，先记录。

### F5（P2，已修复待重部署）vis-network 选项名笔误，图谱物理配置被静默忽略

**现象**：修复后浏览器仍有 **2 条** JS 错误：

```
Unknown option detected: "gravitationalWeight". Did you mean "gravitationalConstant"?
Errors have been found in the supplied options object.
```

**根因**：`services/graph.py:562` 的 vis-network 物理配置写了 `gravitationalWeight`，
而 vis-network 9.1.2（`lib/vis-9.1.2/vis-network.min.js`）里该选项名为
`gravitationalConstant`（实测：`gravitationalConstant` 出现 9 次，
`gravitationalWeight` **0 次**）。vis.js 对未知选项只告警不抛错，所以图谱照样渲染，
但 `barnesHut` 的引力参数**被静默忽略**、退回默认值——属于「能跑但配置没生效」的隐性缺陷。

**定位过程**：`_accept_online.py` 只报「JS 错误 2」不留文本；补了 `js_errors_all`
全量留档后才看到文案。另写 `scripts/_probe_js_errors.py` 走遍 9 页抓错误，
**抓到 0 条**——因为该探针没进图谱页的渲染路径，说明这 2 条与图谱渲染绑定。

**修复**：`gravitationalWeight` → `gravitationalConstant`。已顺带校验模板里其余
12 个选项名（`springLength`/`springConstant`/`centralGravity`/`damping`/
`avoidOverlap`/`stabilization`/`iterations`/`shape`/`scaling`/`smooth`/`arrows`/
`scaleFactor`/`continuous`）在 9.1.2 中全部真实存在。

**状态**：本地全部门禁通过（compileall / unittest 18-18 / smoke_ui 9 页 0 异常 /
smoke_read 60-0 / doc_refs SUSPECT 0），已同步进部署包，**待重部署后复验 JS 错误归零**。

## 8. 踩坑记录（供下轮直接复用）

1. **`/_stcore/health` = `ok` 不代表可用**。本次两个根因它都是 `ok`。唯一可信信号是
   **浏览器里导航 radio 有没有出现**。
2. **「零 JS 错误」也不代表可用**。F2 的指纹就是 0 报错 + 全白；此时看右上角有没有
   `Stop` 按钮——有 = 脚本还在跑，不是坏了。
3. **`sed` 抽取启动壳代码块做隔离测试时，结束正则必须匹配真实缩进**。第一版测试用
   `/^echo "\[start\] ⚠️ 发布包内无 onnx_models/p` 匹配一条**有前导空格**的行，
   永远不命中 → 把 `exec streamlit` 也拖进测试 → 在测试机上真起了服务、退出码假阳。
4. **隔离测试不许用合成目录当源**。第一版 `_test_preseed.sh` 自己造了个符合
   `start_app.sh` 期望的 `onnx_models/…/onnx/`，于是测试全绿；而**真实部署包**的
   文件少一层 `onnx/` 子目录，线上预置会静默失败。改成「用真实部署包当源」后才暴露。
   ——**测试的源数据必须和生产同源，否则测的是自己的假设。**
5. **`mkdir -p` 漏掉最后一级子目录**：`mkdir -p ".../all-MiniLM-L6-v2"` 之后直接
   `cp` 到 `.../all-MiniLM-L6-v2/onnx/xxx`，`onnx` 不存在 → 拷失败。干跑一次就抓到。
6. **`set -e` 下不能用裸 `cp`**：单文件失败会让整个启动壳退出，把「模型没预置上」
   升级成「应用起不来」。逐文件 `cp … || _ok=0`，失败只警告。
7. **emoji 带 U+FE0F 变体选择符，`s[:1]` 切片对不上字面量**。`🕸️` 是 2 个字符，
   `"🕸️ 5. 引用图谱与综述"[:1]` 取到 U+1F578，与 `PAGES` 里的 `"🕸️"`（U+1F578 U+FE0F）
   不相等 → 测试误判 5≠7。**断言要用完整 label 比对，不要用首字符。**
8. **Playwright 的 `.check()` / `.click()` 会被遮罩层拦截**（线上有「未配置 API Key」
   横幅类遮罩），重试 14 次后超时。用 `dispatch_event("click")` 绕过 hit-testing。
9. **子 agent 的 grep 范围要自己复核**。本轮 agent 报「过时表述已清零」，实测它的 grep
   漏了 `docs/review/` 整个目录，里面 3 处旧口径原样留着。**父代必须自己再 grep 一遍。**
