## 6. 缺陷清单与修复优先级

### F1（P0，已修复）Streamlit WebSocket Origin 白名单导致 403

**现象**：页面全白 + 10 条 `WebSocket connection to 'wss://…/_stcore/stream' failed:
Error during WebSocket handshake`。

**根因**：反向代理后面的浏览器连 Streamlit WebSocket 一定带 `Origin` 头，
而 Streamlit 的 `server.corsAllowedOrigins` 默认只含 `streamlit.io` / `*.streamlit.app`
/ `share.streamlit.io` / `localhost`。本域名不在其中 → **HTTP 403** → 页面全白。
`curl -s "$URL/_stcore/host-config"` 可直接看到那个不含本域名的 `allowedOrigins` 数组。

**修复**：启动参数加 `--server.enableCORS=false`。该开关使
`streamlit/web/server/starlette/starlette_websocket.py:189` 的
`is_url_from_allowed_origins()` 直接返回 True，放行所有 Origin。

**验证**：原始 socket 握手测试（`scripts/_ws_handshake.py`）三种 Origin 全部 `101`；
浏览器控制台 WebSocket 报错从 10 条降到 **0 条**。

**残留风险**：`enableCORS=false` 会放行所有 Origin 的 WebSocket 连接。本项目无登录鉴权、
无会话 Cookie、不写敏感数据，风险可接受；该参数与仓库内 `Dockerfile` 的 CMD 一致
（Dockerfile 自 round12 `8cb6b03` 就带了，坏的是仓库外的部署启动器）。

---

### F2（P0，本轮主凶，已修复）embedding 模型同步下载堵死 Streamlit 首帧

**现象**：WebSocket 修复后**仍然全白**，但这次**零报错**。
等待 183s 导航框不出现、9 页点不到、body 仅 4 字。

**根因链**（已逐环取证）：

```
app.py:86             ctx = get_container()                    ← 模块级，首帧路径上
  services/state.py:70   Container.__init__
    services/state.py       _build_embed_fn()
      chromadb onnx_mini_lm_l6_v2.py:269   __call__
        _download_model_if_not_exists()
          → https://chroma-onnx-models.s3.amazonaws.com/all-MiniLM-L6-v2/onnx.tar.gz
            83,178,821 B，sha256 钉版
```

而 Streamlit 的渲染模型是**「整段脚本跑完才发首帧」**。脚本卡在 `_build_embed_fn()`
那一行，一帧都发不出来 → 全白 + 零交互 + 零报错。
唯一线索是右上角的 `Stop` 按钮——它表示「脚本仍在运行」。

**为什么下载完不成**：实测该 S3 域名在境内网络「连接建立但 body 传输挂死」：

```
$ curl -sI https://chroma-onnx-models.s3.amazonaws.com/.../onnx.tar.gz
HTTP/1.1 200 OK                      ← 握手正常
$ curl -s --max-time 5 -o /dev/null -w "%{size_download}"
0 B                                 ← 5 秒 0 字节
```

chroma 的 `tenacity` 重试是 3 次且**每次无超时上限**，下载永不完成。
模型解包后 6 个文件共 91.4 MB（`model.onnx` 90,387,606 B）。

**讽刺点**：`fn(["warmup"])` 这句话术 7 是为**本地提速**故意加在启动期的
（把首问的等待挪到启动期）。本地热缓存下它是优化，**线上冷缓存下它堵死首帧——
同一个优化在不同缓存状态下语义相反**。

**修复（两层，缺一不可）**：

| 层 | 改动 | 作用 |
|---|---|---|
| 代码层 | `services/state.py` 新增 `_EMBED_*`：`warm_embed_async()` / `get_embed_fn()` / `embed_status()`。`Container.__init__` 改为起守护线程后台预热，`embed()` 按需取用并**有界等待**（默认 90s，`AI4S_EMBED_WAIT_SEC` 可调），超时抛人话 `RuntimeError` 指引「可先走 BM25 关键词检索」 | 首帧与模型下载彻底解耦，**任何**冷缓存状态下页面都能出来 |
| 部署层 | 88 MB 的 `onnx/` 随发布包一起上传；`start_app.sh` 在启动 streamlit 前把它拷进 `$HOME/.cache/chroma/onnx_models/all-MiniLM-L6-v2/onnx/` | chroma 的跳过判据是那 6 个文件齐全 → **连下载都不发生** |

**验证（判决性）**：`scripts/_test_coldstart_firstframe.py` 用两个桩复现两种冷缓存状态：

| 桩 | 模拟 | 首帧到达 | 9 个导航目的地 |
|---|---|---|---|
| A | `_build_embed_fn` 抛异常（下载失败） | 5.5s | ✅ 7 radio + 2 按钮全就位 |
| B | `_build_embed_fn` 永久睡眠（**S3 挂死，线上真实形态**） | **1.4s** | ✅ 全就位 |
| C | 模型正常就绪（对照组） | — | ✅ `embed()` 语义不变，0.0ms 直通 |

修复前桩 B 会永远等下去（线上实测 183s+ 无果）；修复后 1.4s 出首帧。

**附带加固（commit `bff3416`）**：模型确实拿不到时，不能把整条功能链路打死。
`_paper_embedding` / `_paper_fingerprints` 失败返回降级值（`None` / `[]`）**并**
把人话原因写进 `ctx.embed_degraded_reason`，文献库页用 `st.caption` 明示
「语义检索模型未就绪…论文已正常入库，但跨版本内容匹配/智能去重暂不可用」
（不用 `st.error`，非致命不刷红）；`ui/page_graph.py` 降级为关键词重合度建边且
口径差异随图谱包持久化；`ui/page_search.py` 相关性得分按 0.0 并说明排序改由
开源代码/点赞/研究画像决定。**每一处降级都对用户可见，没有静默降级。**

### F3（P1，观察项）`start_app.sh` 不在 git 里，与仓库内 Dockerfile 参数分叉

部署用的 `start_app.sh` 是仓库外文件，`git ls-files` 0 命中。而仓库内 `Dockerfile`
自 round12 起就带 `enableCORS=false`。也就是说：**仓库是好的，部署用的是另一套
仓库外启动器**，两边参数不一致且无任何机制保证同步。

本轮 `start_app.sh` 的 mtime 是 23:23:53（我加参数的时刻），一度让人以为"线上跑的是旧启动器"。
**这个推断已被浏览器级证据证伪**：WS 从 403 → 101、JS 报错从 10 → 0，
这两项只有新启动器能带来。但 mtime 风险本身是真的。

**建议**：把 `start_app.sh` 收编进仓库 `scripts/`，部署包里软链过去，消除分叉。
（待办，未实施。）

### F4（P2，观察项）88 MB 模型使部署包从 8.2 MB 涨到 96 MB

预置模型是 F2 部署层修复的必要代价。压缩无效（`gzip -6` 后 82.8 MB，仅省 8%）。
若平台对上传体积敏感，备选方案是把模型改存 git LFS 或对象存储——当前可接受，先记录。
