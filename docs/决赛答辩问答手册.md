## 一、20 个高频问题

| 问题 | 类别 | 标准答案 |
|---|---|---|
| 你们为什么用 Streamlit，不用 React 或 Vue？ | 技术选型 | 我们队里没有专职前端，9 个页面（`_PAGES@app.py:121`）用 React 得先搭路由、状态管理和组件库，工期全砸在界面上，算法这边就空了。Streamlit 让页面和业务同语言，RAG、Chroma、Agent 全是 Python，跨一层语言就多一层故障面，调试也少一层。代价我认：定制受框架限制，所以溯源卡片是我们自己拼的 HTML（`anchor_card@ui/page_qa.py:101`），不是原生组件。真要产品化我会换前端，但比赛比的是算法深度，这个取舍划算。 |
| 向量库为什么选 ChromaDB，不是 Milvus 或 FAISS？ | 技术选型 | 我们要的是"评委一句 `streamlit run app.py` 就能跑起来"。Milvus 得起 Docker sidecar，答辩现场多一个起不来的服务就多一个翻车点，FAISS 又只有向量侧，稀疏检索还得自己接。Chroma 是嵌入式的（`chromadb.PersistentClient@services/state.py:68`），pip 装完即用，同进程句柄直接给 UI 和 Agent 共享。代价我认：规模上限于单机，没有分布式横向扩展。稀疏侧我们用 BM25Plus 自己补（`_build_bm25@services/state.py:108`），选它是因为 idf 恒为正，小语料下不会得零分。 |
| 为什么选智谱 GLM，不用 GPT 或 Claude？ | 技术选型 | 三条。一是 glm-4-flash 文本免费，我们几十轮迭代反复烧不心疼，学生队这是硬约束；二是国内直连，不用给评委准备代理；三是最关键的——它走 OpenAI 兼容协议，换模型不用改业务代码。现在内置 5 个 Provider（`PROVIDERS@core/providers.py:33`），侧边栏切一下就换（`set_provider@services/state.py:126`），服务层完全无感。GPT 也能接，只是现场网络不一定通，不敢拿它做默认。 |
| 你们 ui→core→services→tools 这样分层是为什么？ | 技术选型 | 先纠个顺序：实际是 ui → core/agent → tools → services → storage（`app.py:4`），tools 和 services 是并列的，不是串下来的。这么切是为了把"决策"和"执行"分开——路由、规划、护栏这些决策在 core，检索解析这些业务实现在 services，给 Agent 用的能力封装在 tools。分层不是嘴上说的，依赖方向是干净的 DAG：services 只引 core 的叶子模块（`services/rag.py:40` 引 `core.guardrails`），`core/agent.py:28` 引 tools，`tools/definitions.py:12` 引 services，反向一条都没有，我 grep 验过。这么分的好处很实在：换掉整个 UI 层，Agent 内核和业务服务一行不用动。 |
| 向量模型为什么用 chroma 自带的那个？ | 技术选型 | 384 维，关键是可离线。sentence-transformers 那套要单独下模型，评委断网复现就废了；ONNXMiniLM_L6_V2 随 chroma 依赖分发，本机已缓存，断网也出一样的向量（`_build_embed_fn@services/state.py:43`）。代价我直说：它是英文模型，中文提问配英文文献余弦天然偏低，实测 v1/v7 整篇只有 0.891292，够不上 0.90 阈值。靠分段指纹兜底（`_paper_fingerprints@services/library.py:71`），把全文切五段各算一个向量再取 top3 平均，论文改了名、换了格式照样命中。真要上生产我会换中文模型，但阈值得整套重标，这次来不及。 |
| 你们怎么保证溯源是准的？ | 抗幻觉 | 四道关，跨了生成前中后。生成前：top chunk 相关度低于 0.35 直接拒答，一次 LLM 都不调（`RELEVANCE_FLOOR@services/rag.py:46`）。生成时：系统提示词强制每条事实带角标，还专门写了"禁止自相矛盾"（`ACADEMIC_SYSTEM@core/guardrails.py:470`）。生成后：逐句算锚点覆盖率，低于 15% 判可疑（`check_citation_support@core/guardrails.py:96`）。最后净化：幸存角标按首现顺序重编号，保证【n】和来源一一对应（`sanitize_citations@core/guardrails.py:383`）。四道里三道是代码判定，只有一道靠提示词。 |
| 引用【n】到底怎么映射到原文位置的？ | 抗幻觉 | 喂给模型的上下文长这样："[3] 来源：《1706.03762v7.pdf》 第7页第2段"（`build_context@services/rag.py:709`），页码是解析时带出来的真值，段号由 `annotate_paragraphs@services/rag.py:399` 按该页 chunk 累加算出来。前端那张溯源卡片自带锚点，点"定位第7页"能跨页跳到版式阅读页（`_set_jump@ui/page_qa.py:130`，阅读页在 `ui/page_reading.py:515` 消费）。诚实一句：段号是估算值，150 字重叠和跨页 chunk 会让它漂，所以页级精确、段级近似。 |
| 检索不到的时候，模型会不会自己编？ | 抗幻觉 | 不让它有机会编。检索结果为空、或者最高相关度低于 0.35，直接返回"未在文献库中找到可靠依据"（`REFUSAL_TEXT@core/guardrails.py:44`），LLM 压根不被调用——想编都没地方编。就算进了生成，末尾还有道闸：答案里的数字和实体编号在来源里找不到就进 unverified 列表，尾部附核验说明（`services/rag.py:890`）。空库时还会提示先去传 PDF（`_library_hint@services/rag.py:764`）。 |
| 引用覆盖率低于阈值你们怎么处理？ | 抗幻觉 | 分两种，别混。低于 30% 的是越界角标——【7】这种超出来源数的，先试着按内容重定位到真来源，成功就改指过去（`_recover_citation@core/guardrails.py:367`）；找不到依据就换成"（未在来源中验证）"，绝不硬指。低于 15% 的是内容可疑——这类才值得让 LLM 重写一次，最多 1 轮（`MAX_REPAIR@services/rag.py:47`），防死循环也控成本。这里有个实测教训：越界角标我们原本也丢给修复环，发现修完还是越界，就改成代码直接重定位，省一次调用。修不动就带着 issues 如实展示给用户。 |
| 模型说"我不知道"的机制在哪，靠提示词吗？ | 抗幻觉 | 两层。软的一层在提示词第 3 条：资料不足必须明确写"根据已提供文献无法确定"（`ACADEMIC_SYSTEM@core/guardrails.py:470`）。但提示词靠不住，所以真正兜底的是硬闸门——相关度不够就在调模型**之前**拒答（`services/rag.py:834`），这是确定性的，跟模型心情无关。另外模型真挂了也不会给假答案，降级响应带结构化标记（`DEGRADED_FLAG@core/llm.py:60`），文案写明"不是模型生成"。 |
| 和 Elicit / Consensus / Semantic Scholar / 知网研学有什么本质区别？ | 创新性 | 它们都是"云端文献库 + 问答"，你的本地 PDF 要么进不去，要么进去了不保版面。我们反过来：先做版面感知解析（双栏判定 `_detect_two_columns@services/parsing.py:171`、图注空间匹配、标题树），再谈检索。第二，它们不逐句验引用，我们验（`check_citation_support@core/guardrails.py:96`）。第三，图谱是从你自己的 PDF 参考文献里解析出的真引用边（`build_graph@services/graph.py:201`），不是查平台数据库。 |
| 你们的差异化到底在哪？一句话讲。 | 创新性 | 别人比"答得好不好"，我们比"答错了能不能被抓出来"。三件别人不做的：检索不到就拒答而不是硬答（`RELEVANCE_FLOOR@services/rag.py:46`）；逐句算覆盖率判可疑引用，不是只查角标越界；被引数取不到就打 low_confidence 明说口径，绝不编数字（`_low_confidence_reasons@services/citation_quality.py:456`）。第四条是版面：双栏、图注、公式这些在切块前就处理掉，通用 RAG 直接按文本流切会把左右栏搅在一起。这四条都能当场演示，不是 PPT 上的词。 |
| 你解决了什么别人没解决的痛点？ | 创新性 | 同一篇论文你电脑里存着 v1 和 v7，问 BLEU 值，通用 RAG 会两版混着喂模型：v1 全文写 41.0，v7 只在摘要和表 2 改成 41.8，3:1 的信号比让模型稳定答错。我们的解法在检索层——较新版本在候选池里覆盖够 3 条，就丢掉旧版 chunk（`drop_stale_versions@services/rag.py:91`）。我们试过先在提示词里写规则"以新版本为准"，实测 4 次进程全部无效，最后只能动检索层。改完全库问 BLEU 稳定答 28.4/41.8。这个坑不自己踩过，根本想不到要做。 |
| 版本去重（同一论文多个版本）也算创新吗？ | 创新性 | 我拆开讲，不混着吹。入库去重（`check_duplicate@services/library.py:290`）不算——整篇向量加分段指纹判重，常规做法。真正有价值的是**检索期的版本仲裁**（`drop_stale_versions@services/rag.py:91`）。它不是简单删旧版，而是看新版在池里够不够 3 条（`VERSION_DEDUP_MIN@services/rag.py:55`），够才丢旧版，不够就留着兜底。这个"不够就留"不是保守，是踩过坑：Adam 那个问题 v7 只进了 2 条，旧版的 β2=0.98 是唯一佐证，一刀切去重反而会让 BERT 的 0.999 把答案带偏。所以真正的创新点不是"去重"，是**带阈值的仲裁**。 |
| 引用图谱 + PageRank 这块有什么特别的？ | 创新性 | 图不是从平台 API 拉的，是从你自己 PDF 的 References 章节解析出的真实引用边（`ref_section@services/graph.py:122`、`build_graph@services/graph.py:201`），你传什么就分析什么。PageRank 用 alpha=0.85（`nx.pagerank@services/graph.py:276`，指标汇总在 `analyze@services/graph.py:271`），配入度、介数、特征向量中心性四个指标找基石论文。还有个我挺得意的：Future Work 提取完会顺着引用边查后继论文，已被解决的旧 idea 自动排掉（`explore_future_structured@services/graph.py:972`）。规模我也诚实说：现在库里能进图的只有 2 篇，PageRank 的结论在这个规模下是必然结果，不构成能力证据，所以**我们没敢对外宣称支持 20 篇**。 |
| 你们系统最大的局限是什么？ | 局限性 | 我自己排，第一是本地语料规模。库里现在 5 个文件，按 arXiv 号合并后 3 个独立文档，真正检出引用边进图的是 2 个——赛题说的"20 篇批量文献"我们没有真实实测覆盖，这点不吹。第二是纯中文句的引用校验盲区：锚点只取英文词和数字（`_anchor_tokens@core/guardrails.py:51`），纯中文句锚点少于 2 个就跳过判定。两条都白纸黑字写在技术文档 8.2。 |
| PDF 解析的能力边界在哪？ | 局限性 | 有原生文本层的 PDF 很强，541 页 22MB 的教材我刚在本机跑了一遍，原生文本抽取 4.36 秒，132 万字。边界在两头：一是扫描件，没文本层就必须走多模态 OCR（`ocr_page_text@services/parsing.py:350`），没配视觉模型就降级；二是版面，双栏判定是启发式的（`_detect_two_columns@services/parsing.py:171`），三栏和跨栏表格可能判错，判错了就保守退回单栏。不崩、不阻断，但精度会掉。公式和表格保留下来了，不过表格是文本化进 chunk，还没做结构化单元格检索。 |
| 上下文长度限制怎么解决的？ | 局限性 | 我们不塞整篇，论文多长都不撞窗口。切块 1200 字、重叠 150 字（`CHUNK_SIZE@config.py:134`），向量路和 BM25 路各召回 12 条（`DENSE_K@config.py:136`、`SPARSE_K@config.py:137`），RRF 融合后只留 6 条进上下文（`FINAL_K@config.py:138`）。模型看到的窗口是固定的，跟语料规模无关。代价是跨段落推理会受限，所以我们给跨文献对比加了"每篇保底 3 条"（`COMPARE_PER_PAPER@services/rag.py:49`），不让某一篇被挤没。还踩过一个坑：库里有本大书占了近九成 chunk，会把正确答案挤出 top-k，模型明明有答案却答"无法确定"。修法是把融合池放大到 final_k 的 4 倍再按来源截断（`POOL_FACTOR@services/rag.py:53`）。 |
| 多用户并发你们支持吗？ | 局限性 | 说实话，这块没做，我们只做到"多会话并存"。容器是每个会话一份（`get_container@services/state.py:174`），但写库是整体覆盖——`services/state.py:95` 直接 `write_text` 整个 library.json，没有文件锁。我把代码里所有 Lock 都 grep 了一遍，全是内存缓存锁（比如 `_CLIENT_CACHE_LOCK@core/llm.py:159`），没有一个是保护磁盘写入的。并发上传有丢 chunks 的风险，短期方案是 UI 层串行化入库，这条已经写进技术文档的 Roadmap。 |
| 数据隐私怎么保证？ | 局限性 | Key 只活在内存里——密码框输入（`ui/sidebar.py:212` 的 `type="password"`），存进 `st.session_state`（`ui/sidebar.py:214`），不落盘。校验 Key 时明确不记录内容（函数 `_validate_api_key@core/llm.py:125`，`core/llm.py:130` 注释写明"绝不记录 Key 内容"）。输出侧有脱敏，工具返回和最终答案都过一遍 redact_secrets（`core/agent.py:156` 和 `:664`），`sk-` 开头和智谱那串 32 位十六进制都会打星号。文献和向量库全在本地 storage，不出本机。还有一层是输入侧的：用户粘贴的内容进 Agent 前先过注入检测（`check_injection@core/agent.py:434`），防止 PDF 里的隐藏文字反过来劫持系统提示词。 |

## 二、3 个刁钻问题（单独准备，这三条会被追问）

### 刁 1：「你们用的是智谱 API，那如果智谱明天倒闭怎么办？」

**答：** 倒闭当天换个下拉框就行，不用改代码。因为所有 Provider 走的是同一套 OpenAI 兼容协议，LLMClient 零改动复用（`core/providers.py:4` 的设计说明）。内置 5 个：智谱、DeepSeek、通义、OpenAI、本地 Ollama（`PROVIDERS@core/providers.py:33`）。还有两个逃生口：自定义端点能填 vLLM、LM Studio、硅基流动任意网关（`custom_provider@core/providers.py:103`），以及 `LLM_PROVIDERS_EXTRA` 环境变量加内网网关（`_extra_providers@core/providers.py:77`）。

**但要主动认一条**：真受影响的是扫描件 OCR。5 家平台的视觉能力我实测过 `has_vision`：智谱、通义、OpenAI 三家支持（True），**DeepSeek 和本地 Ollama 两家没有**（False，`vl_model` 为空）。换到这两家之后，扫描件**不是"降级了还能出文本"，而是入库时直接拒收**——`_validate_prepared@services/library.py:484` 在 `services/library.py:510` 写 `scanned_no_ocr`，页面明确提示"全部页面均未提取到文本，**未入库**"（话术档在 `ui/page_library.py:25`）。

所以准确说法是：**文本链路随便换，扫描件入库这条依赖有视觉能力的 Provider**。主动说出来，比被追问出来好。

### 刁 2：「你们的 PDF 解析对扫描件准确率多少？有没有量化测试？」

**答：** 有，但我要先把范围说清楚，不能拿一个数糊弄您。测的是 `pdf/1706.03762v1_img.pdf`——15 页真扫描件，首页原生文本 **0 字符**，`detect_scanned` 判 True。拿它跟同文原生版 `pdf/1706.03762v1.pdf` 的首页逐字对比：

| 指标 | 值 |
|---|---|
| OCR 输出 / 原版首页 | 2790 字符 / 2719 字符，耗时 8.3s |
| 字符级相似度（SequenceMatcher） | **0.960** |
| 词级准确率 / 召回 | **93.9% / 98.5%**（原版 392 词，OCR 383 词：漏 6、多 0、错 18） |
| 真错字 | **1 处**（`nikip@google.com` → `nip@google.com`）；另 17 处"错字"其实是连字修正（`con guration` → `configuration`），属于改进 |
| 关键数字保真 | `28.4` ✅、`41.0` ✅（v1 原文确为 41.0，没串成 v7 的 41.8） |

数据来源 `docs/review/round7_judgeG.md:295-318`。

**三条必须主动说的边界（不说就是给自己挖坑）：**
1. **只测了首页 1 页，不是全篇 15 页。** 单页受 90s 调用超时和 token 成本约束，长篇扫描件只能挑页跑。
2. **VLM 输出逐次不确定。** 另一次跑出来是 2833 字符，且 arXiv 页眉整行漏识别。所以这个数不能当"法律级复制品"承诺。
3. **没有本地 OCR 引擎兜底。** 没配视觉模型，扫描件功能就是没有——不是"效果差一点"，是没有。

### 刁 3：「多用户推荐用的是模拟数据吧？真实场景怎么落地？」

**答：** 您说对了一半，我把真的和假的拆开讲。

**不是模拟的部分**：候选论文是真的，走 arXiv 官方接口实时拉（`search_arxiv@services/extern.py:28`，按分类取最新提交）。打分也是真信号——本地文献库的向量质心余弦、有没有附 GitHub 代码、命中不命中你的研究画像（`_score_rows@ui/page_search.py:259`）。

**您说对的部分**：反馈数据是用户自己点的，按用户 ID 分开存（`_set_like@ui/page_search.py:199`），新用户进来是空的，得真点才有。我们**没有预置任何假的用户行为日志**。

**所以真实落地的门槛不是算法，是冷启动**——没有历史行为的时候，只有主题相似度可用。要做深就得上协同过滤，那需要多用户的真实行为数据，单机版给不出，这是我们的诚实边界，技术文档 8.3 里列的是"长期"项，没吹成已实现。

## 三、可当场复跑的三条命令

答辩现场如果评委要求"证明一下"，跑这三条（必须用 `ai_research` 环境）：

```bash
# 1) 标题抽取 8/8 对照表（含扫描件那一份如实判空）—— 已复跑通过
python scripts/verify_title_extract.py          # 末尾打印：核对通过 8/8

# 2) 单元测试 18 条 —— 已复跑通过，1.5s
python -m unittest discover -s tests -v         # Ran 18 tests ... OK

# 3) 工具接入 21/21 无孤岛（6 个专家白名单覆盖全部 21 个注册工具）
```
